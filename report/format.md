# レポートの形式

`scripts/check.ts` が出す `report.draft.md` は下書き。ここの形式に整え、誤検出の除外・修正案・質問を足してから見せ、`report.md` として保存する。

## 構成

1. 要約（先頭）
2. 🔴 要修正
3. 🟠 要判断
4. 🟡 目視確認
5. ⚪ 手動確認
6. 🟢 合格（件数のみ）

重大度順に固定する。上から読むだけで優先度が分かるようにするため。

## 4区分

| 区分 | ラベル | 意味 |
| --- | --- | --- |
| 修正が確定しているもの | 🔴 要修正 | どんな案件でも直すべきもの |
| 案件次第のもの | 🟠 要判断 | 必要かどうかが案件の仕様やデザインの意図で変わるもの。検出理由を必ず添える |
| 自動では断定できないもの | 🟡 目視確認 | スクリーンショットなどを見て人が判断する |
| スキルの外で行うもの | ⚪ 手動確認 | 実機確認、メール到達、計測タグの動作など |

色が出ない環境（プレーンテキスト、チャットへの貼り付け）でも重大度が分かるよう、絵文字を付ける。

## 件数の数え方

- 要約の件数は**項目数**（指摘の種類）を主とし、括弧で箇所数を添える（例：🔴 要修正 8項目（15箇所））
- 同じ原因の指摘は1項目にまとめる
- 件数は、整形を終えてから最後に確定させる

## 要約

```markdown
# Webサイトチェック レポート

- 対象：http://localhost:3000（12ページ）／構成：Next.js／案件種別：コーポレート（推定）
- プロファイル：標準（所要時間 約12分）
- 件数：🔴 要修正 8項目（15箇所） / 🟠 要判断 6項目 / 🟡 目視確認 2項目 / ⚪ 手動確認 4項目 / 🟢 合格 120件
- Lighthouse（モバイル・参考値）：/ アクセシビリティ 92 / ベストプラクティス 100 / SEO 92
- 優先して見る項目：
  - 全ページで noindex が残っている
  - og:image が未設定
  - 画像 hero.jpg が表示サイズの3.8倍
```

## 各項目の書式

```markdown
- [ ] **og:imageがない**（2件 / /, /about）
  - 箇所：/ ／ `og:imageがない`
  - 理由：SNSやチャットで共有したときに画像が表示されない。
  - 修正案：（フレームワークに合わせて具体的に）
```

- **箇所**は、ページ・要素・可能なら行番号。ソースのファイル名まで特定できるときは書く
- **理由**は、なぜ問題かを1文で。該当するWCAGの達成基準番号があれば付ける（例：WCAG 2.4.4）
- **修正案**は、Next.jsなら `next/image` や `metadata`、WordPressならテーマのテンプレートなど、構成に合わせる
- 同じ指摘が多数あるときは、3件まで例を示し、残りは「ほかN件」にする
- 読み上げ関連は `checks/screenreader.md` の書式に従い、「想定される読み」を断定しない
- 同じ問題を、独自の検査とLighthouseの両方が出していたら1項目にまとめる（例：aria-hidden内のリンク、コントラスト）

## 証跡ファイル

標準・フルでは、目視確認のためのファイルを出力ディレクトリに保存する。レポートでは「証跡：」として相対パスを示す。

| フォルダ | 中身 |
| --- | --- |
| `screenshots/` | はみ出し・ダークモード・強制ダーク・JS無効時・文字拡大・ホバーなし（赤い点線）・フォーカス・各ブラウザ・スマホ端末のスクリーンショット |
| `aria/` | アクセシビリティツリー（スクリーンリーダーに伝わる名前・役割・順番） |
| `print/` | 印刷イメージのPDF |
| `lighthouse/` | Lighthouseの結果JSON（Lighthouse Viewer で開ける）。スコアは `facts.lighthouse` にあり、要約に参考値として載せる（指摘の項目にはしない） |

🟡 目視確認の項目は、証跡を自分（Claude）で開いて確認してから載せる。スクリーンショットを見て明らかに問題がなければ外し、問題があれば🔴や🟠に移して理由を書く。画像を見られない環境なら、そのまま🟡で載せる。

## 要判断の書き方

要判断は、**検出した事実と、なぜ聞くのか**を添える。

```markdown
- [ ] **印刷対応は必要か**
  - 検出：`@media print` の指定がない
  - 判断：印刷される想定がなければ対応不要。会員証・申込書・地図などを印刷する案件なら対応する
```

質問の候補は `report/questions.md`。

## 手動確認の固定項目

レポートの最後に、次を毎回載せる。

- iOS Safari・Androidでの実機確認（アドレスバーの伸縮による `100vh` の見切れ、固定ヘッダー、フォーム入力時のズーム）
- LINEなどのアプリ内ブラウザでの表示確認
- フォーム送信後のメール到達（自動返信・管理者宛）と、迷惑メールに入らないか
- 本番URLでの確認（環境変数で切り替わる noindex・canonical、HTTPSへのリダイレクト、CDN・サーバーのSSL設定、セキュリティヘッダー、圧縮・キャッシュ）。ローカルの検査では、ホスティングやCDN側の設定は確認できないため
- VoiceOverなどでの通し読み（フルでは、Tabキーでの操作は自動で確認している）
- 計測タグ・サーチコンソールの設定（必要な案件のみ）

## 合格項目

件数だけを示す（例：🟢 合格 120件）。内訳は載せない。長くなり、本当に直すべき項目が埋もれるため。

## 修正後のレポート

再検査したあと、次の3つに分けて報告する。

- 修正済み
- 残り（承認されていない項目、判断待ちの項目）
- 新たに出た問題（修正で発生したもの）

## ソースの確認で見つけた項目

スクリプトが検出していない問題に、ソースを読んで気づいたときは載せてよい。項目の末尾に「※ソースの確認で見つけたもの」と書く。プロファイルの範囲外（例：標準でのキーボード操作）なら、フルでの再確認を勧める。

## 保存

`.web-site-check/report.md` に保存し、会話にも表示する。ユーザーのプロジェクトで `.web-site-check/` がGitに含まれないよう、`.gitignore` への追加を提案する（勝手には追加しない）。
