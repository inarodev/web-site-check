# 画像の判断

画像の重さや大きさは、固定のKB上限では判断できない。**表示サイズ・形式・用途に対して大きすぎないか**で判断する。スクリプトは数値を集め、最終的な区分と根拠はここの考え方で決める。

## 形式

- ビルド後に配信される画像がJPEG/PNGのままなら、原則🔴。基本はWebPに変換し、余裕があればAVIFも追加する
- 判定は**ソースの拡張子でなく、実際に配信されたContent-Type**で行う。`next/image` やAstroの `<Image>` は、ソースがJPEG/PNGでも配信時にWebP/AVIFへ変換するため
- 例外として🟠に移すもの
  - OGP画像：一部のSNSでWebP/AVIFが不安定なため、JPEG/PNGが安全
  - `apple-touch-icon`：PNGが標準
  - `<picture>` のフォールバック：WebP/AVIFの `source` の後ろに置いたJPEG/PNGは正当
- ロゴやアイコンがPNG/JPEGなら、SVG化を提案する
- 透過が必要で、WebPにすると品質が落ちて見える画像は、🟡 目視確認にする

## 実寸と表示サイズ

- 表示幅の2倍まではRetina対応として許容する
- 2倍超を🟠、3倍超を🔴にする。ただしヒーロー画像や背景画像は、意図して大きいことがあるため、3倍超でも🟠に下げ、用途を確認する。サムネイル・アイコン・ロゴなど通常の画像は、3倍超なら🔴のままにする
- レスポンシブで表示幅が変わる場合は、最大の表示幅に対する倍率で見る。`srcset` と `sizes` で出し分けていれば、問題は小さい

## 重さ

- 表示面積（2倍密度を想定した画素数）に対して、バイト数が多すぎないかを見る。目安は1画素あたり、WebP/AVIFで0.3バイト、JPEGで0.5バイト程度
  - 例：表示300×200pxの画像が500KBなら、2倍面積（600×400 = 24万画素）で約2バイト/画素となり、明らかに大きい
- この数値は目安。写真の複雑さ（細かい模様が多いほど重くなる）で変わるため、断定しない
- 用途で厳しさを変える
  - ヒーロー・背景：緩め
  - サムネイル・アイコン・ロゴ：厳しめ
  - ファーストビュー内：重いとLCPに直結するため、厳しめ。`loading="lazy"` の有無も見る
- ページ内の画像の合計が数MBを超えるなら、全体として警告する

## レポートの書き方

「大きい」とだけ書かず、根拠と削減の見込みを添える。見込みは概算と明記する。

```markdown
- `hero.jpg`：表示 640×360px、実寸 2400×1350px（3.75倍）、1.8MB
  想定：WebP化＋幅1280pxにリサイズで200〜300KB程度に削減できる見込み（概算）
```

## 修正するとき

- 変換・リサイズの前に、元画像を残す（別ディレクトリへ退避するか、Gitで追跡されていることを確認する）
- Next.js・Astroは、`<Image>` コンポーネントの利用を提案する。静的HTMLは `<picture>` と `srcset`、WordPressはテーマの出力かプラグインで対応する
- 変換ツールは `sharp` など、プロジェクトに既にあるものを優先する
